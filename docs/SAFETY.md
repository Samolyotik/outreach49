# Безопасность: что реально доходит до Telegram

Документ отвечает на один вопрос — «после какой именно команды собеседник
что-то увидит». Всё остальное здесь вторично.

---

## Четыре тормоза, все независимые

```
    ваша команда
         │
    [1]  ├─ статус кампании должен быть active
         │
    [2]  ├─ должен существовать файл var/ARMED
         │
    [3]  ├─ у dispatch должен стоять --confirm
         │
         ▼
    команда легла в очередь Radar
         │
    [4]  ├─ Radar должен её выпустить: билеты лотереи, рампа,
         │   потолок частоты, роль, allowlist, срок годности
         ▼
      Telegram
```

Первые три — наши, и снимаются локально. Четвёртый принадлежит Radar и нам
не подчиняется. Даже полностью «взведённый» bridge49 не может обойти роль
аккаунта, allowlist действий или темп выпуска.

---

## Что не обращается к Telegram вообще

Эти два действия исполняются целиком внутри Radar и не создают ни одного
сетевого запроса наружу:

* `command_dry_run` — разбирает конверт и возвращает имена параметров;
* `gateway_capabilities` — возвращает registry, роль и фактический allowlist.

Ими можно проверять весь путь — постановку, выпуск, чтение результата — не
задевая ни одного собеседника. Демо-кампания построена именно на
`command_dry_run`.

`get_me` — уже настоящий сетевой запрос, хотя снаружи и невидимый.

## Локальные ограничители

`var/limits.json`:

```json
{
  "per_account_daily_visible": 12,
  "per_account_visible_interval_sec": 900,
  "dispatch_batch": 25,
  "send_window_start_hour": 10,
  "send_window_end_hour": 20,
  "send_weekdays": [0, 1, 2, 3, 4]
}
```

| Ключ | Смысл |
|---|---|
| `per_account_daily_visible` | сколько видимых действий в сутки на один аккаунт |
| `per_account_visible_interval_sec` | минимальный промежуток между ними |
| `dispatch_batch` | сколько задач выпускать за один прогон |
| `send_window_*`, `send_weekdays` | окно отправки в рабочей таймзоне |

Проверка дневного лимита выполняется **дважды**: при планировании и ещё раз
непосредственно перед выпуском. Второй раз важен потому, что между планом и
выпуском могут пройти часы.

Ограничители read-действий не касаются: их никто не видит.

## ⚠️ Режим `immediate`

У всех 49 аккаунтов в Radar выставлено
`RESPONDER_OUTREACH.allow_immediate_visible_actions = true`, а планировщик
действий включён по умолчанию. Это значит:

> команда с `mode=immediate` исполнится на ближайшем тике аккаунта,
> в обход лотереи — включая личные сообщения.

Поэтому:

* режим по умолчанию во всех кампаниях — `lottery`;
* `immediate` осмысленен для одиночной проверки (`get_me`, `command_dry_run`),
  но не для рассылки;
* если нужен предсказуемый темп — оставляйте `lottery` и просите владельца
  Radar выдать билеты.

Обратная сторона: пока билетов ноль, `lottery`-команды **не выпускаются
вообще**. Очередь копится и ждёт. Это и есть штатный стоп-кран.

## Идемпотентность: почему нельзя переигрывать новым UUID

`dispatch` пишет UUID запроса в локальную базу **до** обращения к Radar. Если
процесс умрёт сразу после — при следующем прогоне тот же UUID уйдёт повторно,
и мост вернёт уже существующий `command_id` вместо второй отправки.

Отсюда правило: **сомневаетесь — повторите `dispatch`, не создавайте новую
задачу.** Новый UUID после таймаута — единственный способ действительно
задвоить сообщение.

Если Radar вернул `outcome_unknown`, автоматика останавливается и ждёт
человека. Это не сбой, а отказ гадать: результат необратимого действия не
доказан, и повтор мог бы удвоить видимый эффект.

---

## Границы доступа

Роль bridge49 в базе Radar умеет ровно пять вещей: две функции постановки и
три view на чтение. Ей недоступны:

* таблица `account` и любые её поля, включая `config`;
* Telegram-сессии, `api_hash`, пароли прокси;
* смена статусов, попыток, `available_at` и результатов;
* удаление чего бы то ни было.

Поэтому bridge49 физически не может выдать аккаунту новую роль, снять
ограничение или запустить остановленный аккаунт. Всё это — операции владельца
Radar через админ-бота.

## Отмена

| Что | Кто |
|---|---|
| снять запланированную задачу | bridge49: `queue` → отмена задачи |
| отменить уже поставленную команду | оператор Radar: `/tg_outreach_cancel` |
| остановить кампанию целиком | bridge49: `campaigns --status-of … --set-status paused` |
| выключить всё сразу | bridge49: `arm off` |

`arm off` — самое быстрое действие: одна команда, и ни одна новая команда
больше не уйдёт. Уже поставленные при этом останутся в очереди Radar, их
снимает оператор Radar.

---

## Отказы контактов

`bridge49 contacts --opt-out <id> --reason "..."` делает три вещи: помечает
контакт, снимает все его запланированные задачи и закрывает его для будущих
кампаний. Отказ необратим по замыслу — снять его можно только правкой базы
руками, и это должно быть неудобно.
